# VEX firmware change

Read `AGENTS.md`, `docs/HANDOFF.md` and `docs/LOCAL_DEVELOPMENT.md`. Inspect the relevant source before modifying it: `core.h` for rules/persistence, `app.h` for the shared device state machine (controls, calibration, notices, saves), `analyzer.h` for level/pitch analysis, `ui.h` for shared pixels, `flush.h` for dirty bands, `link.h` for the bench packet format, `.ino` for hardware adapters, telemetry and serial switches, and `config.h` for pins.

1. Define the observable behavior and regression risk. Keep boot paused/uncalibrated, stale/clipped/tuner samples and silence longer than the activity hold excluded from practice, and one fragment per completed session.
2. Implement shared behavior in the existing C++ core/app/analyzer/renderer. Keep hardware I/O at the firmware boundary (`.ino` adapters). Never make an audio-callback change that adds display work, logging, allocation or EEPROM writes; `Analyzer::push` is the only interrupt-side call.
3. Add a focused behavioral regression where warranted: a `tests/scenarios/*.txt` script with `expect`/`golden` lines for device behavior or UI, `tests/core_tests.cpp` for pure functions and detector cases. The browser workbench (`make sim`) can record a session as protocol lines (Scenario tab, "Copy as scenario") and replay scenario text with `expect` lines; the native `build/vex-sim` stays the oracle that `make test` runs. After an intentional UI change run `python3 tests/simulator_test.py --update-golden` and review the frames. Injected Hz exercises note math; the `wav`/`raw` commands exercise the shared detector on Mac audio, which is still not codec/gain/latency evidence.
4. For changes to target code, shared headers, pins or dependencies, compile affected target stages (all four before hardware bring-up). Run setup only if dependencies are missing. Redirect verbose output to `build/` and inspect a short error excerpt plus the report. For docs, marketing and packaging changes, reuse existing evidence; do not set up or compile firmware. If the toolchain/download is unavailable, record the exact blocker and stop retrying; manual CI is optional, not a required fallback. Never call host success a target compile.
5. If persistence changes, version/migrate the record and test save/reboot, corrupt latest fallback and old data handling. If pins change, update wiring/BOM/CAD and document the new hardware revision.
6. Update the handoff with commands, results and remaining bench checks. Upload only as a distinct, explicitly intended hardware operation (`make upload STAGE=n`, which needs a compiled image and an explicit `SERIAL=` or exactly one PJRC port); no build/test command should upload.

## Bench loop with a Teensy attached

`make ports` → `make firmware STAGE=n` → `make upload STAGE=n` → `make monitor` (JSON telemetry once a second, link packets summarised) or `make sim DEVICE=auto` and open the workbench **Device** tab (real panel beside the WASM frame, pixel diff, switches, taps, sparklines). Serial switches: `f` full flush, `b` band diff, `1`/`2` cadence × 1/× 2, `l` link streaming, `t` display test pattern (`ui.h` `drawTestPattern`: orientation, colours, band ruler, cadence marker), `-`/`+` SPI clock steps, `g`/`G` codec line-in level, `?` switch and knob state, `m q k` taps and `M Q K` holds through `App::controls`; stage 4 also takes the simulator commands. Knobs boot at the `config.h` values and are never persisted; change `TFT_HZ` or `INPUT_LEVEL` only with a bench number behind it. Every session is logged to `build/bench/<start>.jsonl` by the bridge and `make monitor`; `make bench-report` summarises it against the acceptance rows and the DMA gate (`tools/bench_report.py`, tested by `tests/bench_report_test.py`). `make bench STAGE=n` chains compile, upload and the Device tab. Record `flush_us`/`flush_max_us`, `loop_max_us`, `tx_bytes` and `yin_us` before touching cadence, band merging or the display library; the DMA-driver gate in `docs/HANDOFF.md` is a bench number, not a hunch. Keep the `Panel` adapter the only place that calls the Adafruit pixel API, and keep `link.h` + `tools/link.py` in step (`LinkState` is 76 bytes; both assert it; `tests/link_test.py` decodes the sample `core_tests` writes). Any change to the telemetry JSON or the switch letters must update `docs/LOCAL_DEVELOPMENT.md` §4, the `.ino` header comment, the Device tab's send filter in `tools/web.py` and, if the report reads the field, `tools/bench_report.py`. The order of the first bench sessions is `docs/BRINGUP.md`.

Use staged bring-up 1→2→3→4. Both simulators (native and WebAssembly) share logic and pixels but do not emulate the codec, physical display timing, analog noise or real EEPROM failure timing. Keep those limits clear in any result. A change confined to `simulator/web/` needs `make test` (which includes `tools/web.py check`), not a target compile.

Publish changes using `docs/PUBLISHING.md`. Preserve unverified target/bench status until actual evidence changes it. Never route build logs, binary data or repeated encoding/bridge chunks through chat.
